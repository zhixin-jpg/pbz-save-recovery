# 案例：共用账号的新档经 Steam 云同步覆盖旧进度

这是一次真实事故的记录，时间范围为 2026-11-01 至 2026-11-03。账号 ID、安装路径等个人信息已隐去。

## 结果先说

- 旧进度没有丢，只是被新档的云存档顶掉了。
- 游戏本地保留了 `1RealTime`、`2Hourly`、`3Daily` 三组历史备份。
- 从 `2Hourly` 中找到最后一份真实进度，覆盖回 `PBZSaveGame.sav` 后，解码校验和游戏内显示都正确。

## 时间线

| 时间 | 发生了什么 |
|---|---|
| 11-01 22:45 | 最后一次真实自动存档：磐镇，主线 `MainCh2-SiZhen`，游戏时长 15 小时 29 分，死亡 68 次，尘埃 33492 |
| 11-01 23:04 | 出现一份西古、时长约 1 小时 16 分的新档 |
| 11-02 20:45–20:58 | 新档继续推进到约 3 小时 |
| 11-03 17:25 | 新档已到 3 小时 06 分 |
| 11-03 18:00 | 开始排查：当前档、三组备份、Steam 云状态 |
| 11-03 18:37 | 用 11-01 22:45 的备份覆盖当前档，MD5 一致；解码验证通过 |

## 怎么判断是云覆盖

1. 当前 `PBZSaveGame.sav` 解码后是西古、3 小时的新档。
2. 但 `2Hourly` 里还有 11-01 22:45 的旧进度，内容是磐镇、15 小时 29 分。
3. 两份存档的关卡、时长、主线完全不同，说明不是同一段进度的后续，而是两条独立的游戏线。
4. Steam 的 `remotecache.vdf` 显示云同步状态为已同步，本地文件被云端版本替换过。

结合账号是共用的，可以还原出大致过程：另一边用同一账号新开了一局，新档上传云端；本机联网启动时，云端的新档覆盖了本地旧档，之后所有自动备份都围绕新档生成。

## 恢复步骤回顾

1. 完全退出 Steam，确认 `steam.exe` 不在运行。
2. 把整个账号存档目录（含三组备份）复制到独立目录，共 29 个文件、约 9.2 MB。
3. 逐个解码备份，按存档内的关卡、时长、主线筛选，锁定 `2Hourly` 中 11-01 22:45 那份。
4. 将该文件复制为 `PBZSaveGame.sav`，校验 MD5 一致。
5. 用 pbz-save-manager 的源码重新解码当前档，确认关卡、时长、存档点、死亡次数、尘埃都对。
6. 先以离线模式启动 Steam 验证，再处理云同步：关闭该游戏的云存档，或冲突时选择保留本地文件。

## 为什么没有选"最新"的备份

最新的备份（11-03 17:26）属于新档，虽然是最后生成的，但内容和旧进度无关。**备份文件名的新旧只代表写入时间，不代表进度属于你**。真正可靠的是解码后的关卡、游戏时长和主线任务。

## 教训

- 发现不对，第一件事是退出 Steam、复制整个存档目录，而不是启动游戏确认。
- 三组历史备份是回档的关键，只备份当前档没有用。
- 回档后不要立刻联网启动；云端那份错误存档还在，会再覆盖一次。
- 共用账号要约定设备，或者至少关闭云存档，避免互相覆盖。
